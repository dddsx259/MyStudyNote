## 1. 什么是死锁 (p.5–6)

### 1.1 定义

**死锁 (deadlock)**: 一组线程, 每个都持有某些系统资源, 并阻塞等待另一线程持有的资源; 全体都无法继续, 系统陷入停顿。

课件描述 (p.5): 「全系统范围的资源请求纠缠 (system-wide tangle of resource requests), 所有请求都无法满足, 整个系统停摆。」

### 1.2 例子

**例 1 (磁盘)**: 系统有两台磁盘驱动器。T1 与 T2 各持一台, 各自还需要另一台 → 互相等 → 死锁。

**例 2 (二值信号量)**:

```
T0                  T1
wait(A)             wait(B)
wait(B)             wait(A)
```

T0 持 A 等 B, T1 持 B 等 A → 循环等待 → 死锁。

## 2. 死锁为何发生 (p.7)

- 若能提前检测到这些情况, 死锁或许不会发生
- 但 **有时看不到线程如何用锁**:
  - 大型代码库, 依赖复杂
  - 调用外部库函数, 封装隐藏了实现细节 (不知内部持哪些锁)

课件例子:

```c
Vector vec1, vec2;
Thread1:                  Thread2:
    :                         :
    vec1.AddAll(vec2);       vec2.AddAll(vec1);
    :                         :
```

为避免竞态, `AddAll()` 可能需要同时锁住两个 Vector。两个线程以相反顺序调用 → 可能死锁, 而调用者根本不知道。

## 3. 哲学家就餐问题 (Dining Philosophers) (p.8–9)

### 3.1 问题设定

**哲学家就餐问题 (dining philosophers problem)**: 五位哲学家围圆桌而坐, 每人面前一盘意面, 相邻两人之间一支叉子, 共五支。每位哲学家循环「思考 → 吃面」, 吃面需要 **同时拿起左右两支叉子**。设计一个 **无死锁、无饥饿、并发度高** 的并发程序。

课件注: 「这问题出名是因为有趣且有点智力挑战; 但实际效用低。」关键在于证明解 **无死锁、无哲学家饥饿、并发度高**。

### 3.2 朴素解法

```c
philosopher() {
    while (true) {
        think();
        eat();
    }
}
eat() {
    pickupLeftFork();
    pickupRightFork();
    eatingSpaghetti();
    putdownRightFork();
    putdownLeftFork();
}
```

**这解法可行吗?** 若所有哲学家 **同时** 拿起左叉 → 每人都等右叉 → 循环等待 → **死锁**。这是死锁四条件同时成立的典型场景, 也是后续讨论的引子。

## 4. 死锁的四个必要条件 (p.10–11)

**死锁的四个必要条件 (four necessary conditions for deadlock)**: 死锁发生当且仅当以下四条 **同时** 成立; 破坏任一条, 死锁就不可能发生。

| 条件 | 含义 |
|---|---|
| **互斥 (mutual exclusion)** | 资源在同一时刻只能被一个线程独占访问 |
| **持有并等待 (hold-and-wait / wait-for)** | 线程可持有一些资源的同时等待获取额外资源 |
| **不可抢占 (no-preemption)** | 资源不能从持有它的线程那里被强制夺走 |
| **循环等待 (circular-wait)** | 两个或更多线程形成环, 每个线程都在等待环中下一个线程持有的资源 |

### 4.1 资源分配图 (resource-allocation graph) (p.11)

```
T1 --hold--> R4
T1 --wait--> R3
T2 --hold--> R3
T2 --wait--> R4
```

T1 持 R4 等 R3, T2 持 R3 等 R4 → 形成环 → 循环等待成立。

## 5. 死锁预防 (Deadlock Prevention) (p.12–14)

**死锁预防 (deadlock prevention)**: 用 **限制性策略 (restrictive policy)** 在资源分配时破坏四条件之一, 使死锁不可能发生。代价是降低资源利用率或编程灵活性。

### 5.1 破坏循环等待 (Prevent Circular-Wait)

**方法**: 对所有资源类型施加 **全序 (total ordering)**, 要求每个线程 **按递增顺序** 申请资源。

```
T1 --hold--> R3 --wait--> R4   ✗ (应先拿 R3 再拿 R4? 不对, 全序要求先小后大)
T1 应先请求 R3, 再请求 R4
```

**缺点**:
- 实际程序未必按此顺序用资源; 但被要求先持有小编号资源才能拿大编号资源 → 资源利用率低
- 哲学家就餐: 给叉子编号, 要求每人都先拿编号小的叉子再拿编号大的 → 但需先识别左右哪支编号小

### 5.2 破坏持有并等待 (Prevent Hold-and-Wait)

**方法**: 线程在 **开始时一次性申请全部所需资源**, 要么全拿到, 要么什么都不拿 → 不会出现「持有一些又等另一些」。

**缺点**:
- 资源利用率低 (线程持有暂不用的资源, 他人无法用)
- 可能饥饿: 请求多资源的线程要等很久, 因为策略偏向小请求的线程

### 5.3 破坏互斥 (Prevent Mutual Exclusion)

**方法**: 对 **可共享 (sharable)** 资源允许非互斥访问, 则不会死锁。

**缺点**: 多数共享资源 **不支持或无法正确** 在非互斥访问下工作 (如写操作必须互斥)。

### 5.4 破坏不可抢占 (Prevent No-Preemption)

**方法**: 线程持有资源时若请求新资源不可得, 必须 **释放已持有的全部资源**, 等到能同时获得旧资源加新资源时再重启。

**缺点**:
- 开销大: 释放资源可能丢失已完成的工作, 或须 undo 已做的部分才能重启
- 例: John 转 100 给 Mary, 需「John 减 100」+「Mary 加 100」两步, 半成功不允许 → 若中途须释放, 已做的减法要回滚
- 可能饥饿

## 6. 死锁避免 (Deadlock Avoidance) (p.15–18)

**死锁避免 (deadlock avoidance)**: 不预先破坏条件; 而是 **在知道各线程全部资源需求** 的前提下, 调度线程使死锁不发生。需要 **全局知识 (global knowledge)** — 各线程运行中可能申请哪些锁/资源。

两种方法:
1. **基于调度的避免 (avoidance by scheduling)**
2. **银行家算法 (Banker's algorithm)**

### 6.1 基于调度的避免 (p.16)

根据各并发线程的资源需求, 看依赖关系, 据此调度以避免死锁。

课件例子:

|  | Thr1 | Thr2 | Thr3 | Thr4 |
|---|---|---|---|---|
| R1 | need | need | no | no |
| R2 | need | need | need | no |

若系统让 Thr1 与 Thr2 在不同 CPU 上并发 → 可能死锁 (都要 R1, R2)。保守做法: 把 **不冲突** 的线程分到同一组并发 (如 Thr4 与 Thr1/Thr2/Thr3 任一), 把 **可能死锁** 的线程串行化。

**缺点**: 保守, 资源利用不足。

### 6.2 银行家算法 (Banker's Algorithm) (p.17–18)

**银行家算法 (Banker's algorithm)**: 允许线程持有资源的同时请求更多资源; 系统仅当 **授予后状态仍安全 (safe)** 时才分配, 否则让线程等待。

- **安全状态 (safe state)**: 用剩余资源存在一种分配顺序, 能满足所有线程的未来需求, 使所有线程都能成功终止
- **不安全状态 (unsafe state)**: 可能 (但不一定) 导致死锁

#### 数据结构 (单类资源例子, p.18)

| 线程 | max() | loan() | claim() |
|---|---|---|---|
| T1 | 4 | 1 | 3 |
| T2 | 6 | 4 | 2 |
| T3 | 8 | 5 | 3 |

- `max()`: 声明的最大使用量
- `loan()`: 当前已分配
- `claim() = max() − loan()`: 未来还能请求的量
- `total = 12`: 资源总数
- `available = total − Σloan() = 12 − (1+4+5) = 2`: 剩余可用

#### 安全性判定 (p.18 课件问)

**问**: 若 T1 请求 1 单位, 系统应授予吗? 若 T2 请求 1 单位呢?

**判定流程** (安全性检查):
1. 试分配: `available -= 1`, 该线程 `loan += 1`, `claim -= 1`
2. 找一个 `claim ≤ available` 的线程, 假设它跑完并归还全部 `loan` → `available += loan`
3. 重复直到所有线程都完成 → 安全; 若中途找不到这样的线程 → 不安全, 不授予, 让请求者等待

**T1 请求 1 单位**: 试分配后 `available = 1`, T1 `claim = 2, loan = 2`。
- T1 `claim=2 > available=1`? 不能立刻满足, 但 T2 `claim=2 > 1`? 也不行; T3 `claim=3 > 1`? 也不行 → 找不到可完成的线程 → **不安全**, 不授予

**T2 请求 1 单位**: 试分配后 `available = 1`, T2 `claim = 1, loan = 5`。
- T2 `claim=1 ≤ available=1` → T2 可完成, 归还 `loan=5` → `available = 6`
- T1 `claim=3 ≤ 6` → T1 可完成, 归还 `loan=2` → `available = 8`
- T3 `claim=3 ≤ 8` → T3 可完成 → 全部完成 → **安全**, 授予

#### 银行家算法的弱点

- 须 **事先知道** 各线程的最大资源需求
- 只在 **线程数与资源数固定** 时工作
- 资源变化 (如设备故障变不可用) 时, 算法失效, 因为可能把状态变不安全
- 实际 OS 较少使用 (开销与假设太强), 多用于教学

> 2023 Final Q6 银行家大题 (20 分) 即按此: 给 Max/Allocation/Need/Available, 请求要 **试分配后再判安全**, 且新进程独立于上一问。见 `test&quiz/Final01 2023-12-13 解析.md`。

## 7. 检测与恢复 (Detection & Recovery) (p.19)

**检测与恢复 (detection and recovery)**: 实用方案, 允许死锁偶尔发生, 周期性检测并处理。

课件引文: 「若坏事很少发生, 就不值得花大力气去预防它, 尤其是坏事发生的代价小。」

### 7.1 检测

- 系统周期性检查死锁是否发生
- 识别涉及的进程与资源
- 通常检查 **资源分配图是否存在环 (cycle)** — 有环即循环等待成立

### 7.2 恢复

- **方案 1**: 终止所有死锁进程
- **方案 2**: 一次终止一个进程, 直到死锁环消除
- 逐次抢占资源, 直到死锁不再存在
- 无论哪种, 一些进程成为 **牺牲者 (victims)**
- 通常要求进程 **从头重启** 或 **从上一个检查点 (checkpoint) 恢复**

## 8. Summary (p.20)

- 死锁是并发程序 (OS, 多线程程序, 高并行程序) 中常见且严重的问题
- 死锁发生时, 四个必要条件 **必然同时** 出现
- 三类对策对比:

| 对策 | 思路 | 程序员/系统职责 |
|---|---|---|
| **预防 (prevention)** | 用限制规则破坏某一必要条件 | 程序员须在程序中应用规则 |
| **避免 (avoidance)** | 用全局资源使用知识指导分配 | 程序员可自由安排逻辑; 系统负责避免策略 |
| **检测与恢复 (detection & recovery)** | 允许死锁偶发, 周期检测并恢复 | 多数时候开销小, 恢复时较费力 |

## 9. 与 Lec08 的衔接

- Lec08 末尾「交换 sem_wait 顺序」是死锁的典型场景: 先拿 `mutex` 再等 `empty` → 持有并等待 + 循环等待 → 死锁
- 哲学家就餐的「全拿左叉」也是循环等待
- 预防循环等待 → 给叉子/资源编号, 按序申请 (Lec09 §5.1)
- 银行家算法要求线程 **事先声明最大需求**, 这正是「全局知识」的来源 (Lec09 §6.2)
