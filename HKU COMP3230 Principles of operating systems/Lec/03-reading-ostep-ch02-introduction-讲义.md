## 1. 程序如何运行 (开篇)

运行中的程序做一件很简单的事: **执行指令**. 处理器每秒数百万乃至数十亿次:

1. 从内存 **取指 (fetch)**
2. **译码 (decode)**
3. **执行 (execute)** (加减、访存、条件、跳转等)

然后下一条, 直到程序结束. 这就是 **冯·诺依曼计算模型 (von Neumann model)** 的基础.

现代 CPU 底层会乱序、并行执行多条指令, 但程序通常仍假设指令 **看似** 一次一条、按序执行.

程序运行时, 还有大量「野事」发生, 目的是让系统好用. 负责这些的软件体就是 **操作系统 (operating system, OS)**: 让系统以正确、高效、易用的方式运转.

**预备阅读建议** (书中点名): Patt & Patel [PP03]; Bryant & O'Hallaron [BOH10].

## 2. The Crux: 如何虚拟化资源

**核心问题 (crux)**: OS **如何** 把资源虚拟化?

- **Why** 不是重点 (答案显然: 更好用)
- 关注 **how**: 用什么 **机制 (mechanism)** 与 **策略 (policy)**? 如何高效? 需要何种硬件支持?

书中用 shaded box 标出各章要解决的 crux; 章内细节给出解法或解法的基本参数.

### OS 的三重说法

1. **虚拟化**: 把物理资源 (处理器、内存、磁盘等) 变成更通用、强大、易用的虚拟形态 → 有时把 OS 叫做 **虚拟机**
2. **接口 / 标准库**: 导出数百个系统调用, 供运行程序、访存、访问设备等
3. **资源管理器**: 多程序共享 CPU / 内存 / 设备时, 由 OS 管理, 目标可为效率、公平或其他

早期别名: **supervisor**; 甚至 **master control program** (书中玩笑: 见电影 *Tron*).

## 3. §2.1 虚拟化 CPU (Virtualizing The CPU)

### 例子 `cpu.c` (Figure 2.1)

循环: `Spin(1)` 空转约 1 秒 → `printf` 打印命令行字符串 → 永远重复. `Ctrl-c` 可终止前台程序.

单实例运行很无聊; 若一次启动多个:

```text
./cpu A & ./cpu B & ./cpu C & ./cpu D &
```

输出交错出现 A/B/C/D. **只有一个 (或少量) 物理 CPU**, 却仿佛有很多程序同时在跑.

这就是 **CPU 虚拟化**: OS (借助硬件) 制造「有极多虚拟 CPU」的幻觉, 让许多程序 **看似** 同时运行. 本书第一大部分即围绕此主题.

要启动/停止/指定跑谁, 需要与 OS 通信的 **API**. 多程序同时想跑时, **谁先跑** 由 OS 的 **policy** 回答 → 再次体现资源管理器角色.

(`&` 在 zsh 等 shell 中把作业放到后台; 不同 shell 细节略异.)

## 4. §2.2 虚拟化内存 (Virtualizing Memory)

### 物理内存模型

内存可看成字节数组: 读要给地址; 写还要给数据. 程序运行时不断访存 (数据结构的 load/store); **每条指令本身也在内存里**, 取指也要访存.

### 例子 `mem.c` (Figure 2.3–2.4)

- `malloc` 一块 `int`, 打印地址与 `getpid()`, 循环递增并打印
- 单进程: 地址如 `0x200000`, 值 1,2,3,…
- **两进程同时跑**: 两者打印的虚拟地址可以 **相同** (`0x200000`), 但各自独立递增 → 仿佛每进程有私有内存

实际上: OS 在做 **内存虚拟化**. 每进程有私有 **虚拟地址空间 (virtual address space)** (常简称 address space), 由 OS 映射到物理内存. 一进程内的访存不影响其他进程 (或 OS) 的地址空间; 对进程而言仿佛独占物理内存, 现实却是共享资源由 OS 管理.

注: 演示需关闭 **地址空间随机化 (address-space randomization)** (安全特性, 可防部分攻击; 书中建议自行了解, 勿鼓励搞破坏).

## 5. §2.3 并发 (Concurrency)

**并发**: 在同一程序里「同时做很多事」时出现的一整类问题. 问题最初出现在 OS 自身 (在进程间切换); 现代 **多线程 (multi-threaded)** 程序同样面对.

### 例子 `threads.c` (Figure 2.5)

- `main` 用 `Pthread_create` 建两个线程, 都跑 `worker`: 循环 `counter++` 共 `loops` 次, 再 `Pthread_join`
- `loops=1000` 时终值常为 2000 (期望 `2N`)
- `loops=100000` 时终值可能是 143012、137298 等 **错误且不稳定** 的值; 有时又碰巧正确

### Crux: 如何构造正确的并发程序?

同地址空间内多线程并发时, 如何写正确程序? OS 需提供什么原语? 硬件提供什么机制? 如何用来解并发问题?

**原因直觉**: `counter++` 在机器上通常是三条指令 (load → increment → store), **非原子 (not atomic)**. 交错执行会丢更新. 本书第二部分详论.

(书中 `Pthread_*` 大写是作者 wrapper, 实际调用小写 `pthread_create` 等.)

## 6. §2.4 持久化 (Persistence)

- DRAM 等内存 **易失 (volatile)**: 断电/崩溃则数据没
- 需要硬件 + 软件 **持久存储**: 硬盘 (HDD)、固态盘 (SSD) 等 **I/O 设备**
- OS 中管理磁盘的软件通常叫 **文件系统 (file system)**: 可靠、高效地把用户文件存到盘上

与 CPU/内存抽象不同: OS **通常不为每个应用造私有虚拟磁盘**; 用户往往要 **共享文件**. 例: 编辑器写 `.c` → 编译器读入生成可执行文件 → 再运行.

### 例子 `io.c` (Figure 2.6)

三次系统调用: `open` (创建/打开) → `write` → `close`. 请求路由到文件系统, 返回错误码等.

文件系统实际写盘很繁琐: 决定数据落在盘上何处、维护元数据、对设备发 I/O. **设备驱动 (device driver)** 懂具体设备接口. OS 通过系统调用提供标准、简单的访问方式 → 又像「标准库」.

性能上常先 **延迟写、批处理**; 为应对写过程中崩溃, 常用 **journaling (日志)** 或 **copy-on-write (写时复制)** 等写协议, 仔细排序写盘以便恢复. 数据结构从简单链表到复杂 B-tree 等.

### Crux: 如何持久存储数据?

文件系统负责持久数据. 正确性要什么技术? 高性能要什么机制与策略? 硬件/软件失败下如何可靠?

## 7. §2.5 设计目标 (Design Goals)

OS 做: 虚拟化物理资源、处理并发、持久保存文件. 设计时要有目标以便做 **权衡 (trade-off)**.

| 目标 | 含义 |
|---|---|
| **抽象 (abstraction)** | 方便易用; CS 处处依赖抽象 (高级语言、汇编、门电路分层等) |
| **高性能 / 低开销** | 虚拟化值得, 但不能任意贵; 开销含额外时间 (指令) 与空间 (内存/磁盘) |
| **保护 (protection)** | 应用之间、应用与 OS 之间; 恶意或意外行为不伤害他者/OS |
| **隔离 (isolation)** | 保护的核心原则: 隔离进程 |
| **可靠性 (reliability)** | OS 尽量不停机; OS 挂则应用全挂; 现代 OS 代码庞大, 可靠性仍是研究热点 |
| 其他 | **能效**; **安全** (保护的延伸); **移动性** (小设备) 等 — 场景不同目标权重不同 |

原则常跨设备通用.

## 8. §2.6 简史 (Some History)

更丰富材料见 Brinch Hansen [BH00].

### 早期: 几乎只是库

- OS 起初主要是常用函数库 (如底层 I/O API), 方便开发者
- 大型机上常由人工操作员一次跑一个程序; **批处理 (batch processing)**: 作业成批提交. 机器太贵, 不宜交互闲置

### 超越库: 保护

- OS 代表系统跑的代码特殊 (控制设备), 不能当普通库随便调
- 若任意应用可读磁盘任意处 → 无隐私; 文件系统不宜纯库实现
- **系统调用** 思想 (Atlas 等先行): 特殊硬件指令 + 硬件状态, 使进入 OS 成为受控过程

**系统调用 vs 过程调用**:

- 系统调用转入 OS, 同时 **提升硬件特权级**
- 应用跑在 **用户态 (user mode)**: 硬件限制 (通常不能随意发磁盘 I/O、访问任意物理页、发包等)
- 经 **trap** 等特殊指令: 硬件转到预设 **trap handler**, 并升到 **内核态 (kernel mode)**; OS 可满权限操作
- 完成后经 **return-from-trap** 回到用户态与原中断点

### 多道程序时代 (Multiprogramming)

- 小型机降价 → 更多人能碰计算机 → 创新加速
- **多道程序设计**: 内存中装多个作业并快速切换, 提高 CPU 利用率; I/O 慢时切到别的作业
- 推动: **内存保护**、中断下的 **并发正确性** 等
- 实践上重大进展: **UNIX** (Ken Thompson, Dennis Ritchie, Bell Labs); 吸收 Multics 等思想但更简; 源码磁带流传

### Aside: UNIX 的重要性

- 小而强的程序可组合; **shell** 与 **管道 (pipe)** 做元级编程, 如 `grep foo file.txt | wc -l`
- 对程序员友好, 带 C 编译器; 早期近乎开源分发
- 内核小、可读 → 他人可改; Berkeley **BSD** (Bill Joy 等) 推进 VM、文件系统、网络; Joy 后参与创办 Sun
- 商业化与法律纠纷曾拖慢传播 (SunOS, AIX, HPUX, IRIX 等); Windows 崛起于 PC

### 现代与 PC

- PC (Apple II, IBM PC) 普及桌面; 早期 OS 曾 **倒退**: 如 DOS 弱内存保护; 早期 Mac OS 协作式调度, 死循环可拖死整机
- 后来桌面重新吸收小型机教训: macOS 以 UNIX 为核心; Windows NT 起大幅前进; 手机 (如 Android/Linux) 更像 1970s 小型机 OS 而非 1980s PC

### Aside: Linux

- Linus Torvalds 自写 UNIX 风格系统 (借思想不借受版权纠缠的代码基), 结合 GNU 工具 → **Linux** 与现代开源运动
- 互联网公司广泛用 Linux; Android 亦基于 Linux; Jobs 把 NeXTStep (UNIX 系) 带到 Apple → 桌面也有 UNIX
