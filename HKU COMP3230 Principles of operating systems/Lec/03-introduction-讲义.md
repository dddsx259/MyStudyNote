## 1. OS 是什么 (p.5)

操作系统 (operating system, OS) 是一个 **程序**, 它:

- **控制**应用程序的执行 (谁先跑、跑多久、谁被挂起或换出等)
- 承担两大主功能:
  1. **资源管理器 (resource manager)**: 管理 CPU、内存、磁盘、文件等; 在冲突请求间做高效且公平的裁决
  2. **应用与硬件之间的接口**: 把应用与其访问的硬件隔开; 通过 **应用程序接口 (API, Application Program Interface)** 让程序向 OS 请求服务/资源, 从而简化应用开发

---

## 2. 核心服务与问题焦点 (p.6–7)

### 2.1 Core Services

OS 至少要支持:

1. 让应用在计算机上运行
2. 让运行中的应用使用并共享内存
3. 让运行中的应用彼此交互
4. 让应用访问并共享持久存储上的数据

### 2.2 The crux

焦点不在「为什么要 OS」(答案显然: 更好用), 而在 **how**:

- 用什么 **机制 (mechanism)** 与 **策略 (policy)** 支撑上述服务?
- 如何高效?
- 需要何种硬件支持?

## 3. 四大核心职能 (p.8–15)

### 3.1 进程与处理器管理 (Process & Processor Management)

- **进程 (process)**: 基本上是 **正在执行的程序**
- 进程需要资源: CPU、内存、I/O、文件、初始数据; 终止时要回收可复用资源
- 系统上通常有许多进程 (用户进程 + OS/内核/系统进程), 在一或多个 CPU (核) 上并发运行

OS 要回答:

| 问题 | 含义 |
|---|---|
| 如何管理/控制应用进程? | 多进程共存 |
| 如何执行受限操作? | 如 I/O 等特权操作 |
| 如何提供「多 CPU」幻觉? | 每进程仿佛独占处理器 |
| 如何重新夺回 CPU? | 即使进程不合作 |
| 如何设计有效调度器? | 往往没有进程特征的完美先验知识 |

### 3.2 内存管理 (Memory Management)

- **冯·诺依曼计算模型 (von Neumann model)**: 指令与数据必须在物理内存中才能执行
- 目标: 在有限内存与多进程并发下, 决定哪些内容应在内存中, 以优化 CPU 利用率与响应用户

OS 要回答:

| 问题 | 含义 |
|---|---|
| 如何共享单一物理内存池? | 给每进程私有地址空间抽象 |
| 如何控制可访问的内存位置? | 防止写别的进程内存 |
| 总需求超过物理上限怎么办? | 借助更大更慢的磁盘 |
| 如何管理空闲空间? 耗尽时? | 可从运行进程处回收内存 |

### 3.3 并发 (Concurrency)

- OS 本身是并发程序: 多个执行逻辑可能同时更新内核内部数据结构
- 现代多核 + 多线程普遍; 同地址空间内多任务共享数据时, 必须用合适的 **同步原语 (synchronization primitives)** 才能正确

OS 要回答: 需要哪些同步原语? 硬件/OS 如何支持其正确与高效? 如何用它们解并发问题?

### 3.4 文件管理 (File Management)

- 管理存储磁盘的组件称为 **文件系统 (file system)**
- 以可靠、高效方式把用户数据存到磁盘
- 提供信息存储的统一逻辑视图: 把物理属性抽象为逻辑单元 — **文件 (file)**; 并把文件映射到物理介质, 提供管理/访问机制

OS 要回答: 如何管理持久设备 (新建/删除文件时找/释空间)? 磁盘上要哪些数据结构 (按文件名找数据)? 如何降低 I/O 代价 (磁盘慢)?

## 4. OS 的目标 (p.16)

1. 让系统方便易用
2. 在应用之间、以及 OS 与应用之间提供 **保护 (protection)**
3. 高效使用资源
4. 能在多种硬件配置上运行
5. 高度可靠: 不因孤立的应用/硬件错误而整体失效
6. 保护资源免受用户与软件的未授权访问

## 5. OS 结构概览 (p.17–18)

典型分层示意 (自上而下):

1. **Shell (命令壳)**: 用户与 OS 交互的界面
2. 实用/库函数层: 供应用程序与命令层调用的一组 utility
3. **Kernel (内核)**: OS 核心; 管理资源并直接与硬件交互
4. 硬件

## 6. 用户态、内核态与系统调用 (p.20–21)

### 6.1 User Mode & Kernel Mode

CPU (至少) 有两种模式:

| 模式 | 又称 | 何时 | 能力 |
|---|---|---|---|
| **内核态 (kernel mode)** | privilege / supervisor mode | 内核代码执行时 | 最高特权, 可执行机器上任意指令 |
| **用户态 (user mode)** | — | 用户应用执行时 | 较低特权, 仅可用指令子集 |

用户态限制保证: 一个用户程序不能执行会干扰其他用户程序运行的指令.

### 6.2 System Calls

- **系统调用 (system call)**: 应用程序向 OS 请求资源/服务的机制; 系统调用集合构成 OS 服务的接口 (API)
- 发生系统调用时: 从用户态切到内核态, 执行对应内核系统函数 — 称为 **模式切换 (mode switch)**
- 靠特殊指令实现: 进程 **陷入 (trap)** 进内核, 再 **return-from-trap** 回到用户态

## 7. OS 架构 (p.19, 22–30)

架构用来: 组织组件功能; 规定各组件以何种特权级执行. 常见选项如下.

### 7.1 单体架构 (Monolithic Architecture)

- 每个 OS 组件都在内核内
- 早期往往未把组件建成清晰模块接口; 各部分交织成一大块特权程序
- 组件间可直接通信 (如函数调用); 数据结构易共享

**优点**: 往往很高效率.

**缺点**:

- 组件可直接碰硬件; 架构相关代码易散落全内核
- 可直接访问彼此数据/函数 → 改一处牵一处
- 一组件的 bug 易波及其他; 微妙错误难定位
- 更易受恶意组件破坏

### 7.2 分层架构 (Layered Architecture)

- 把功能相近的组件编成模块, **一层叠一层**
- 每层只与紧邻上下层通信; 请求可能穿过多层才被服务
- 效率通常低于单体内核

**优点**:

- 构造与调试更简单: 可从最低层调起, 逐层加上去
- **信息隐藏 (information hiding)**: 每层只知紧邻下层接口
- 可用另一实现替换一层而不牵动其他
- 设计者可选择在何处划内核/用户边界

**虚拟机 (virtual machine) 作为分层例子** (p.26):

- **虚拟机监控器 (virtual machine monitor)** 又称 **hypervisor (管理程序)**
- 可跑在宿主 OS 之上 (用户态) 或并入宿主 OS (内核态)
- 虚拟化硬件资源, 让每个客户 OS 以为自己控制整机 (实为虚拟机)
- 本质上是「OS 的 OS」

### 7.3 微内核架构 (Microkernel Architecture)

- 尽量把功能从内核空间挪到用户空间进程 (**servers**)
- 保持内核小; 仅最基本部分跑在内核态 → 更稳, 更易扩展与移植

**优点**: 可扩展、可移植、可伸缩; 更安全可靠 (内核态代码更少).

**缺点**: 用户态 server 靠 **消息传递 (message passing)** 交互, 需经内核 → 通信开销显著, 性能常有损失.

### 7.4 模块化途径 (Modular Approach)

- 多数现代 OS 仍采用 **单体架构**, 但实现为 **内核模块 (kernel modules)**
- 各核心组件分离为模块; 整个内核是模块集合

相对分层更灵活高效, 因为:

- 每模块有良好定义的受保护接口; 模块间可相互调用
- 都在内核内通信更高效
- 允许按需 **动态加载模块 (dynamically loadable modules)** → 省内存
- 可单独改模块并容易加新模块

**例子**: Solaris, Linux, 传统 Unix 内核.

## 8. Summary (p.33)

1. OS 是资源管理器: 在用户间协调资源使用, 并向用户提供计算机的抽象视图.
2. 不同架构各有利弊; **现代 OS 倾向: 单体 + 分层思想 + 内核模块**, 以兼顾扩展性.

## 对照速记

| 架构 | 效率 | 隔离/可靠性 | 扩展性 |
|---|---|---|---|
| Monolithic | 高 | 相对弱 | 改动牵连大 |
| Layered | 中偏低 | 较好 (信息隐藏) | 可替换层 |
| Microkernel | 常偏低 (IPC) | 强 (内核小) | 强 |
| Modular (on mono) | 较高 | 中等+ | 动态模块强 |
